# Control-plane Minimal Governance Core v0

Date: 2026-05-13
Lane: Falcon / Falcon Lab
Status: active minimal governance core

## Purpose

This file compresses the useful part of the Green / Yellow / Red control-plane into one active governance core.

It exists so dated ops artifacts can stop acting like active truth.

This file does not approve deletion, archive movement, source reading, public use, runtime movement, review execution, or knowledge promotion.

It also replaces approval-seeking control-plane work with result-first Falcon execution.

Codex should optimize for useful, reviewable SCIMA/FCHMA results, not for producing approval paperwork.

## Active Truth Rule

Active truth is limited to:

- `AGENTS.md`;
- `PLANS.md` as the current GTD surface;
- this Minimal Governance Core after Founder acceptance;
- current SCIMA/FCHMA methodology, review-gate, source-manifest, packet, registry, claim-index, and expert-agent infrastructure artifacts that are explicitly in their own kernel locations.

Dated ops artifacts are historical by default.

Codex must not treat dated ops artifacts as active instructions unless they are explicitly named in `PLANS.md` or in this file.

## Result-first Work OS

Approval defines the working boundary. It does not make weak output acceptable.

Within the approved boundary, Codex is responsible for producing the best concrete deliverable it can.

Default loop:

1. Start from the requested outcome.
2. Confirm only the minimum necessary constraints.
3. Execute one bounded vertical slice.
4. Produce a concrete artifact or useful output.
5. Report what was produced, why it is useful, assumptions, uncertainty, next improvement, and any hard boundary reached.

Do not stop for approval unless the task would cross a hard boundary.

For reversible choices inside the approved boundary, Codex should make a reasonable decision, state assumptions compactly inside the deliverable when useful, and continue.

Avoid creating meta-documents unless the requested deliverable is itself method, governance, or review design.

Do not create dashboards, progress monitors, no-content/no-write receipts, heartbeat files, branch selectors, supervisor chains, or status-accounting documents unless Founder explicitly requests them.

Falcon's priority work is SCIMA/FCHMA knowledge-network construction:

- case signal maps;
- preliminary interpretations;
- structured hypothesis evaluations;
- candidate interaction propositions;
- pattern cells;
- Pattern Candidate Cards;
- human audit packs;
- reviewed knowledge object candidates after human review;
- expert-agent grounding from reviewed knowledge.

Deprioritize dashboards, receipts, Green / Yellow / Red chains, no-content/no-write documents, generic strategy writing, and public IA/SNS/site strategy before knowledge grounding.

## Hard Boundaries

Stop and return a short decision request only when a task would require:

- reading raw sensitive case/source/feedback content beyond explicit authorization;
- quoting or exporting sensitive text or PII;
- legal, medical, HR, accommodation, employment, or case correctness judgment;
- source validity or support validity judgment;
- review-status movement;
- knowledge promotion;
- `candidate_pattern`, Domain Core, Atlas / 27-frame, public-safe, public-approved, or runtime-approved movement;
- public IA, site, SNS, release, or public claim movement;
- current Japan factual or policy claims without explicit authorization;
- runtime, retrieval, schema, provider, model, prompt, route, DB, or test behavior changes;
- deletion or irreversible file movement;
- external research unless explicitly authorized.

## Green

Green means same-boundary work only.

Green may proceed when it does not read raw/source/case/feedback content, does not change public/runtime/schema/model/provider/prompt/route/DB/test behavior, does not create or change review status, and does not promote knowledge.

Green is for small maintenance, verification, formatting, compact indexing, or bounded artifact preparation that does not change product meaning.

Green must not become autonomous paperwork continuation. Green should produce useful concrete results inside the approved boundary.

## Yellow

Yellow means boundary design only.

Yellow may clarify a future Red decision by defining scope, allowed inputs, allowed outputs, stop conditions, and approval wording.

Yellow must not execute the boundary movement it designs. Yellow should be compact and should not multiply approval packets.

## Red

Red means boundary movement or execution.

Red requires explicit Founder / Pro approval before execution.

Red includes content reading, review execution, source/support validity judgment, public-facing movement, runtime/retrieval/schema/model/provider/prompt movement, review-status movement, Domain Core / Atlas / 27-frame movement, `candidate_pattern` movement, public-safe/public-approved movement, runtime-approved movement, and knowledge promotion.

## Code Red

Code Red stops autonomous continuation.

Use Code Red when Falcon may be producing apparent progress while missing the SCIMA/FCHMA knowledge-network purpose.

During Code Red, routine Green continuation, dashboard work, receipt work, and progress-monitor work stay paused unless Founder / Pro explicitly reopens them.

Code Red should redirect work toward a concrete kernel-recovery result, not toward more monitoring paperwork.

## Raw Content

Codex must not read, quote, summarize, compare, synthesize, or transform raw/source/case/feedback content without explicit scope approval.

When approval exists, Codex must stay inside the exact corpus, record set, field set, and output shape approved.

Raw text must not be exported or quoted unless explicitly approved.

## Public / Current Claims

Codex must not create public IA, site, SNS, campaign, source-policy, current Japan, legal, employment, HR, medical, or accommodation claims without a separate public/source approval gate.

Public delivery surfaces are downstream of reviewed knowledge, not substitutes for the knowledge network.

## Runtime

Codex must not change runtime, retrieval, schema, provider, model, prompt, route, DB, tests, telemetry, audit, retention, or PII behavior without explicit architecture approval.

Infrastructure existence is not knowledge growth by itself.

## Promotion

Machine-generated fingerprints, clusters, candidate cards, claim-index entries, strategy docs, dashboards, and receipts are not reviewed knowledge.

No item may move into reviewed reusable knowledge, `candidate_pattern`, Domain Core, Atlas / 27-frame, public-safe, public-approved, runtime-approved, or promotion status without explicit human review and separate Founder / Pro approval.

## Human Review

Human review is mandatory for reviewed knowledge.

Codex may prepare review tools, candidate structures, comparison surfaces, and audit scaffolds.

Codex must not perform the human review, fabricate reviewer status, infer approval, or convert a human-owned task into an AI-owned result.

## Cleanup Rule

Control-plane cleanup is allowed only to remove clutter from active truth.

Cleanup must not become a substitute for SCIMA/FCHMA knowledge growth.

Archive movement requires separate Founder approval.

Deletion requires archive first, verification, and a later separate Founder approval.

## Completion Report

Use chat/final response as the receipt.

At the end of each task, report only:

1. what concrete deliverable was produced;
2. why it is useful;
3. what assumptions were made;
4. what remains uncertain;
5. what the next iteration should improve;
6. whether any hard boundary was reached.

Do not create a separate receipt file unless explicitly requested.
