# Axiom Development Charter v0

Date: 2026-06-07
Lane: Falcon Lab
Codename: Axiom
Status: next-core development charter / no runtime, prompt, retrieval, DB, schema, model, provider, public approval, publication, or knowledge promotion movement

## Position

Axiom is the next core-development codename after Falcon.

Axiom does not mean a small repair of the currently published Falcon-based NBL site. It means rebuilding the original first objective that Falcon did not adequately secure:

> a FCHMA-style interaction-hypothesis reasoning kernel that creates usable provisional hypotheses by binding observation, inference, counter-hypothesis, missing context, and implementation conditions into an intermediate object.

The NBL site, SNS operation, articles, diagrams, consultation interfaces, and public explanation layers should be rebuilt as interfaces to that kernel.

## Why Axiom Exists

Falcon made real progress in public surfaces, visual/multimodal direction, SNS operation, boundary visibility, and knowledge-governance scaffolding.

But Falcon likely failed at the original first objective because the expert-agent reasoning kernel was not held as the active done boundary. When bureaucratic work was stopped, the correction moved work forward but did not strictly re-anchor every outcome-producing slice to the kernel.

Axiom exists to prevent that specific failure from repeating.

## Falcon Inheritance And Bootstrap Rule

Axiom must not be confused with Falcon, but it does not start from an empty repo.

Axiom may share Falcon's evidence foundation:

- original secure survey datasets
- staging / analysis-ready derived data
- web-cache and official-source cache
- source manifests and data-quality profiles
- Stage 1 SCIMA/FCHMA derived artifacts
- L3 principal interaction patterns and cross-cutting axes
- FT03 internal expert-agent response contract
- existing boundary and public-risk lessons

But Axiom must not inherit Falcon's public interface as its core truth.

Use Falcon material as bootstrap priors, not as promoted Axiom doctrine.

Allowed bootstrap use:

- seed the first interaction-hypothesis kernel contract
- seed scenario evaluation fixtures
- seed source-lens and missing-context expectations
- seed L3 pattern candidates and cross-cutting checks
- seed public-boundary and actionability-band language
- compare Axiom kernel outputs against Falcon-derived expectations

Forbidden bootstrap use:

- treat Falcon public pages as proof that the core kernel exists
- treat Falcon outputs as reviewed Axiom knowledge
- promote Falcon-derived materials into Axiom without labeling their status
- copy Falcon delivery-layer interfaces before the kernel passes scenario evaluation
- count Falcon site/SNS progress as Axiom core progress

The bootstrap label must be explicit:

- `falcon_bootstrap_prior`
- `shared_evidence_foundation`
- `axiom_kernel_candidate`
- `requires_axiom_eval`

The rule is:

> Axiom can use Falcon's knowledge to start faster, but every inherited frame must pass through Axiom's kernel evaluation before it becomes Axiom core.

## Next NBL Site Backcasting Rule

The Axiom-based next NBL site should not restart public-site IA by trial and error.

The basic content composition may inherit the final Falcon-based NBL site composition as a site skeleton, while replacing the concrete content with Axiom-updated content grounded in the interaction-hypothesis kernel.

Inherited site skeleton:

- reader-facing top / home
- work-condition window / condition-category entrances
- consultation case-reading collection
- inherited 21 views / work-design guide slot, rebuilt as kernel-derived work-design views whose count is not fixed
- theory / method / trust page
- article / social-question library
- cognitive support toolkit / studio / multimodal teaching objects
- about / operating-boundary page
- SNS operation as an external circulation route back to the same theme objects

But this skeleton is delivery architecture, not Axiom core truth.

The inherited "21 views" name is a site-composition prior, not a final Axiom view count. L3's 21 principal interaction patterns and six cross-cutting axes are bootstrap seeds for Axiom eval. They may be kept, merged, split, renamed, dropped, or held for missing context before becoming public-readable work-design views.

The development order should be backcast from the final content composition:

1. Fix the final site composition and navigation roles first.
2. Define the Axiom theme object that can feed all surfaces.
3. Define which kernel fields each surface must expose, translate, hide, or route to review.
4. Generate Axiom-updated content from the kernel object into each surface slot.
5. Implement pages by filling stable content slots, not by discovering the IA through page-by-page experimentation.
6. Only widen the site skeleton when a kernel-backed content need cannot fit the inherited structure.

Required labels:

- `falcon_site_composition_prior`
- `axiom_content_update_required`
- `kernel_backcast_required`
- `delivery_layer_not_core_kernel`

Forbidden moves:

- rebuild the public IA before the kernel object and content slots are defined
- treat Falcon page copy as Axiom content without kernel backcasting
- count inherited page structure as Axiom core progress
- create new public sections because a page feels incomplete
- optimize UI polish before the kernel-backed content slots exist

The rule is:

> Axiom should inherit Falcon's final content composition as a map, not as content. Build the next site by backcasting from that map to the kernel object, then forward again into public-readable surfaces.

## Core Done Boundary

Axiom core progress exists only when a slice strengthens at least one of:

- `kernel_build`
- `kernel_eval`
- `kernel_grounding`
- `kernel_display`
- `kernel_human_review_loop`

Everything else is delivery-layer progress, even if valuable.

Examples of delivery-layer progress:

- public page rebuild
- SNS post pipeline
- article library
- diagram or image set
- interface polish
- explanation copy

These may proceed only when they expose, translate, test, or route the kernel. They must not be counted as core progress by themselves.

## Human Review Rule

Human review must not become a universal stop button.

Axiom keeps human review as the gate for:

- final professional judgment
- public release
- source validity
- support validity
- `candidate_pattern`
- `runtime_approved`
- `public_safe`
- `public_approved`
- Domain Core / Atlas / 27-frame movement
- learning updates from outcomes
- intervention validity or support recommendation finality

But human review must not block:

- creating provisional hypotheses
- generating counter-hypotheses
- extracting missing-context questions
- classifying actionability bands
- running non-sensitive scenario evaluations
- improving deterministic kernel logic
- creating internal draft outputs clearly labeled as provisional
- building UI that displays provisional kernel objects
- preparing reviewer packets from already-labeled provisional objects

The rule is:

> Review blocks promotion, publication, finality, and learning updates. Review must not block provisional reasoning, evaluation, or interface work that remains clearly internal and non-final.

## Human Review Compression Rule

Human review must not be required for hundreds of generated instance-level hypotheses.

That would repeat Falcon's failure mode: provisional knowledge work becomes an approval queue, and the project stops before the reasoning kernel becomes useful.

Axiom uses review compression:

- Review the reusable framework layer, not every generated hypothesis.
- Review pattern families, views, bands, and gates before they become promoted reusable knowledge.
- Let the kernel generate provisional instance-level hypotheses under reviewed framework constraints.
- Require human review only when a provisional hypothesis is promoted, published, used as final judgment, or fed into learning updates.

The practical human-review budget for core meaning should stay under 100 review units.

High-value review units include:

- the interaction-hypothesis kernel contract
- the actionability bands
- the L3 principal interaction patterns
- the cross-cutting check axes
- the scenario-evaluation archetypes
- the public-boundary language rules
- the promotion / publication / learning-update gates

Reviewing Falcon's 21 views or a Heron-like 27-frame level is realistic and necessary.
Reviewing hundreds of one-off hypotheses is not realistic and must not be the core workflow.

## Required Intermediate Object

Axiom must produce an intermediate object before final answer rendering.

Minimum object fields:

- observation
- inference
- counter-hypothesis
- missing context
- implementation actor conditions
- source-lens status
- actionability band
- cannot-yet-say limits
- human-review route

The final public or internal interface is a translation of this object, not a substitute for it.

## Actionability Bands

Axiom must avoid the Falcon failure mode where the system has only two modes:

- overconfident recommendation
- boundary-only refusal

Use at least these bands:

- `usable_provisional_insight`
- `question_first_only`
- `hold_or_research_needed`
- `public_boundary_blocked`

Each band should define what can proceed without human review and what remains blocked.

## Anti-Swamp Rules

Stop and redirect when work creates:

- receipts without kernel improvement
- review checklists without scenario evaluation
- dashboards that do not display or route the kernel object
- prompt rewrites without eval fixtures
- public pages that do not expose the kernel's way of seeing
- SNS pipelines that do not route back to kernel-building themes

If a slice does not strengthen the kernel, label it honestly as delivery-layer or non-core work.

## Current Non-Goals

- Do not patch the current Falcon-based public site as if that solves the core issue.
- Do not start from a new public homepage.
- Do not start from SNS growth.
- Do not start from prompt rewriting.
- Do not start from exhaustive source review.
- Do not wait for complete human review before building provisional kernel/eval machinery.

## First Axiom Sequence

1. Freeze the current Falcon public site except for urgent safety or factual-risk fixes.
2. Build non-runtime L3 expert-agent scenario evaluation.
3. Implement the typed interaction-hypothesis kernel contract.
4. Add deterministic kernel generation or validation for synthetic fixtures.
5. Display the kernel object in an internal review surface.
6. Only then redesign the next public site and SNS interfaces around the kernel.

## Success Test

Axiom is not succeeding because the site looks new.

Axiom is succeeding when a concrete input can reliably produce:

- observations
- inferences
- at least one counter-hypothesis
- specific missing-context questions
- implementation actor conditions
- source-lens status
- a provisional actionability band
- a human-review route

and when the public/site/SNS interface can translate that object into language that ordinary readers can understand without turning it into final advice.
