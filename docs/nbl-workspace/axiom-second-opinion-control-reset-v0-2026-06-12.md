Date: 2026-06-12
Lane: Falcon Lab / Axiom
Status: active control addendum; no publication, public approval, runtime, prompt, retrieval, model/provider, DB/schema, source/support validity, candidate_pattern, or learning-update movement

## Purpose

This addendum incorporates the 2026-06-12 external second opinion into the active Axiom development discipline.

The second opinion agreed that the Axiom epistemic design is strong, especially the reality-shadow treatment of incomplete evidence, source-lens discipline, counter-hypothesis / missing-context handling, and stratified minority-signal protection. It also identified a real swamp risk: governance shells, review receipts, and release gates were growing faster than the actual Axiom domain-knowledge-to-site product surface.

The control reset below is therefore adopted as a development rule, not as another review layer.

## Current Goal

Use the Founder-accepted Axiom integrated domain knowledge object as the substance source for the next NBL internal candidate page bodies.

The current accepted substance source is:

- 10 all-layer integrated-domain knowledge units
- 37 substructures
- pre-Founder autonomous review findings
- employment-phase coverage audit
- upper-disability-category layer
- source-lens boundary notes

This replaces the earlier Falcon/L3-derived page-body drafts as substance. Falcon final-site purposes, page roles, layout rhythm, and visual scaffolding may remain delivery scaffolding.

## Control Rules

### 1. Freeze new release-gate shell growth

Do not add new Gate 8 / final-release / public-navigation / Founder-decision shell, receipt, payload, handoff, validation, ingestion, or return-hold modules while the next concrete work is page-body projection.

Existing Gate 8 artifacts remain historical/internal hold scaffolds. They must not be expanded as the main path.

If release decision work is later needed, compress it into one typed workflow object with states such as `prepared`, `reviewed`, `decided`, and `executed`, rather than another chain of shell objects.

### 2. Keep one active Founder review target per cycle

The active reviewed object is the all-layer 10-unit / 37-substructure Axiom integrated domain knowledge receipt.

Do not generate a new Founder review object before the accepted knowledge has been projected into readable next-NBL internal candidate page bodies. Intermediate renderings may be created for comprehension, but they must not become new approval targets unless the user explicitly requests a new review cycle.

### 3. Treat tests as regression guards, not truth proofs

Jest tests may guard structure, coverage, layer separation, source-lens boundaries, no-public/no-runtime/no-learning movement, and preservation of corrected counts or classifications.

They do not prove that the domain interpretation is true. When analysis legitimately changes, tests should help reveal what changed; they must not become a substitute for methodological review.

### 4. Continue the product-critical path

The next shippable increment is not another receipt layer.

The next shippable increment is:

1. Build Axiom-backed internal candidate page bodies for the next NBL site from the accepted 10 units and 37 substructures.
2. Preserve Falcon page purpose and layout scaffolding only as delivery context.
3. Make each public-like page show how the Axiom knowledge object is translated, simplified, hidden, or routed to later public-copy review.

### 5. Keep runtime/model evaluation as a separate later kernel-eval track

The second opinion correctly notes that the final product must eventually test whether an actual model can obey the Axiom kernel discipline at inference time.

That work should be designed later as an offline, sandboxed `kernel_eval` harness: model outputs in, evaluation receipts out, no publication, no learning update, no production runtime, no provider commitment, and no public navigation.

It is not the current page-body projection slice.

### 6. Keep PLANS.md short enough to steer

Long Axiom status chains should move to dated artifacts like this one. `PLANS.md` should state current status, next action, hard boundaries, and links to supporting artifacts, rather than becoming the full operational ledger.
