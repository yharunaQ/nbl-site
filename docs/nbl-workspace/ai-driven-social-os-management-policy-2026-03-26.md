# AI-Driven Social OS Management Policy

更新日: 2026-03-26
Status: working management policy

## Purpose

この文書は、NBL の経営方針のピボットを、今後の AI 経営チームと Founder 判断の基準として固定するための memo。

今回ここで明文化したいことは 4 つ。

1. NBL を `AIドリブンの社会OS事業` としてどう経営するか
2. 当面の主市場を `障害者雇用に関わる企業` と `障害者就労支援者` に置く理由
3. `赤字でも進める product-first period` をどう扱うか
4. インフォグラフィックや動画の `投げ銭的収益` を、どの位置づけで許容するか

## Working Conclusion

- NBL の主事業は、障害者雇用の企業と障害者就労支援者向けに、再利用可能な方法論、workflow、AIツール、resource を作って提供する `AIドリブン社会OS事業` として進める
- 初期は `収益最大化` より `product fit / repeated use / artifact compounding / trust compounding` を優先する
- したがって、当面の赤字運営は `失敗` ではなく `R&D と operating layer 構築コスト` として許容する
- ただし、完全に収益感覚を失わないために、インフォグラフィックや動画の `任意支援・投げ銭的収益` は `bridge revenue lane` として持ってよい
- 重要なのは、`content support revenue is allowed, but it is not the business core` を明示すること

## What is currently usable

- Usable now (with conditions):
  - `product-first, revenue-later` を初期方針として受け入れる
  - 主市場を `企業` と `障害者就労支援者` に置く
  - `startup fee + recurring + bounded usage` を本命 revenue stack として維持する
  - インフォグラフィック / 動画の任意支援を `bridge revenue lane` として持つ
  - content lane を `distribution + signal acquisition + small cash support` として使う
- Not yet usable:
  - 投げ銭収益を主事業として扱うこと
  - 診断名別 advice や個別高リスク判断を content monetization と結びつけること
  - コンテンツ収益を理由に sensational な disability framing へ寄ること
  - `寄付をくれたら個別相談や優先対応をする` と読める運用

## Bias / Discrimination Risk

- Risk level: medium
- Risk factors:
  - 障害や難病の困難を強く dramatize した方が投げ銭が集まりやすい、という incentive が生まれる可能性
  - lived experience や就労困難を、一般化しやすい short video language に圧縮しすぎる可能性
  - `困っている人を助けるための寄付` という framing に寄ると、NBL の `社会OS product company` としての輪郭がぼける可能性
  - content 収益が伸びると、企業・支援者向け product の build より media optimization に drift する可能性
- Guardrails:
  - `診断名 -> 解決策` の直結を避ける
  - `person / job / environment / support / time / institution` の文脈が抜ける内容で強い約束をしない
  - 当事者の困難そのものを monetization hook にしない
  - essential educational resources は paywall に入れない

## Management Principles

### 1. Product first, patronage second

- NBL の本命は `企業 / 支援者向け product と operating layer`
- supporter revenue は `時間を買うための橋` であり、主戦場ではない

### 2. Public resources are distribution assets before monetization assets

- 図解や動画の第一目的は、信頼形成、理解促進、need discovery、next conversation の発生
- 収益化は secondary benefit として扱う

### 3. Red ink is acceptable when compounding is real

- 初期は赤字でも、artifact、loop、trust、distribution、revenue capacity が増えているなら進めてよい
- 逆に small revenue が出ても、product の核が育っていなければ成功と見なさない

### 4. The first paying logic must stay B2B / professional

- `最初にしっかり払う相手` は、企業か支援者側の professional user であるべき
- 一般向け投げ銭は `supporter lane` であり、顧客定義そのものではない

### 5. Disability-related monetization needs stricter ethics than generic creator monetization

- 困難、差別、制度 gaps を clickbait や fear-based monetization に使わない
- 当事者の脆弱性や企業の不安を煽って conversion を上げない

### 6. Revenue hierarchy must stay explicit

- `bridge revenue` と `core revenue` を混同しない
- `content audience` と `professional buyer` を混同しない

## Revenue Hierarchy

### Layer 0. Bridge revenue: supporter / tip-style contributions

- role:
  - 制作継続のための小さな cash support
  - どのテーマに resonance があるかを見る signal
  - Founder が `少しは収益を得る感覚` を失わないための補助線
- units:
  - infographic release note
  - video explainer
  - public-safe audio / visual campaign artifact
  - optional supporter note
- rules:
  - access 自体は free を基本にする
  - payment は gratitude / support の性格に留める
  - ケース対応、優先返信、個別判断とは結びつけない

### Layer 1. Product startup revenue

- invitation-only startup package
- private workspace setup
- initial workflow / knowledge / boundary pack

### Layer 2. Recurring product revenue

- private workspace subscription
- knowledge updates
- workflow maintenance
- bounded professional usage

### Layer 3. Metered usage revenue

- assessments
- agent runs
- credit burndown

### Layer 4. Later narrow outcome-linked revenue

- workflow completion のような限定された operational outcome にのみ適用
- accommodation judgment や雇用意思決定そのものにはかけない

## What content support revenue is for

- 制作継続の小さな原資
- public interest の signal acquisition
- mailing list / inbound / referral の補助線
- `この資源は役立つ` という micro-validation

## What content support revenue is not for

- NBL の主 revenue thesis の代替
- vulnerable user から小口で資金を集める慈善モデル
- 高リスクな個別判断の対価
- `無料では見せない重要情報` の paywall 化
- 企業向け product build からの逃避

## Allowed monetization patterns

- optional tip button
- supporter message / thanks note
- free public release + optional support
- series continuation support for infographic / video lane
- low-pressure CTA that clearly says `支援は任意`

## No-go monetization patterns

- pay to unlock safety-critical or practically essential accommodation guidance
- pay for diagnosis-specific answer or legal-sensitive recommendation
- emotionally manipulative fundraising copy
- `困っている当事者のために寄付してください` を主 language にすること
- sponsor expectation that distorts evidence or editorial independence
- supporter payment と professional product access を混ぜること

## Default operating allocation

初期の時間配分は、次を default とする。

- 55%: core product / method / workflow / private layer build
- 20%: public resources and distribution assets
- 15%: partner discovery and professional revenue validation
- 10%: supporter revenue lane, campaign lane, lightweight monetization ops

もし supporter revenue lane がこの比率を食い始めたら、`伸びている` ではなく `drift risk` として再評価する。

## Decision Rules

### Keep bridge revenue lane active when

- 制作継続の足しになる
- public reach や signal quality が改善する
- product build の時間を壊していない
- sensationalism を強めなくても支援が集まる

### De-prioritize or stop it when

- content optimization が product build を食う
- distortion や clickbait 圧力が高まる
- general audience 向け media business に寄り始める
- `NBL = 支援寄付メディア` に見え始める

## Success Metrics

### Core business metrics

- professional user の repeated use
- design partner / pilot conversation 数
- startup fee or recurring につながる実名案件数
- private layer の usage quality

### Bridge revenue metrics

- supporter conversion rate
- content 1本あたりの optional support 額
- content からの qualified inbound 数
- returning supporter ratio

### Guardrail metrics

- product build 時間の圧迫がないか
- high-risk comment / misunderstanding が増えていないか
- disability framing が単純化されていないか

## Founder Boundary

Founder が今回持つべき判断は次の 5 つだけでよい。

1. `Keep`
   - product-first period を維持するか
2. `Name`
   - supporter lane を public で何と呼ぶか
3. `Yes / No`
   - optional support button を各 content lane に置くか
4. `Adjust`
   - 企業向け product と支援者向け product の比重
5. `Stop`
   - supporter lane が NBL の輪郭を崩す時点

## Immediate next action

- `Revenue Architect` と `Managing Director` は、以後 `Layer 0 = bridge revenue, Layer 1+ = core revenue` を前提に議論する
- public copy では `応援支援は任意` と `professional product is the main business` が両立するようにする
- infographic / video lane を monetization する場合でも、まず `free public value` を先に返す
- 最初の検証は `1-2 本の動画 or infographic series` で行い、product build を止めない範囲で運用する

## Bottom line

- NBL は `AIドリブン社会OS product company` として進める
- 障害者雇用の企業と障害者就労支援者向けの product build が本命
- 当面の赤字は許容する
- ただし、インフォグラフィックや動画の `投げ銭的収益` は、主事業を壊さない条件つきで `bridge revenue lane` として採用してよい
- 収益の小ささを焦って consulting drift や sensational media drift に戻らないことが、今回の経営 guardrail である
